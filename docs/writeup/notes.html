Background: chess basics

Only what a reader needs to follow the results. A single box or figure may be enough.

How a position is written: FEN

  • Forsyth–Edwards Notation describes a whole position on one line: piece placement rank by rank (from rank 8 down), side to move, castling rights, en passant square, and two move counters.
  • Upper case is White, lower case is Black; digits count empty squares.
  • This is what every benchmark prompt gave the models. Show one example and decode it in a figure:

rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq e3 0 1

(The starting position after 1.e4: Black to move.)

How a move is written: SAN

  • Standard Algebraic Notation: piece letter plus destination square (Nf3), x for a capture, + check, # mate, O-O castling, e8=Q promotion. Pawn moves have no letter (e4).
  • The models answered in SAN. A move is legal only if it is possible in that exact position for the side to move.

Legal moves

  • The tricky rules cause many illegal answers: you can't leave your own king in check, pinned pieces can't move off the pin line, plus castling conditions, en passant and promotion.
  • A typical puzzle position here has about 27 legal moves. That sets the chance level for "picked the best move".

Evaluation and tactics

  • Evaluation: who is better and by how much, in centipawns (100 cp ≈ one pawn). +150 means White is about 1.5 pawns better.
  • Tactics: short forcing sequences such as forks, pins, skewers and mate-in-N. Lichess tags each puzzle with themes like these. The T3 theme mark checks for them.
  • Lichess puzzles: real positions from online games, where one move (the "setup move", usually a mistake) gives the other side a tactic. The benchmark shows the position before that move (Issue 21).

Background: how chess engines work

Classical engines (Stockfish style)

  • Search: build a tree of moves and replies several moves deep. Minimax assumes both sides play their best; alpha-beta pruning skips branches that can't change the result, so the engine searches much deeper for the same work.
  • Evaluation function: scores the positions at the end of the search: material, king safety, piece activity, pawn structure.
  • Stockfish now uses a small neural network (NNUE) for its evaluation, but is still search-heavy. check before citing

Neural engines (AlphaZero / Lc0 style), which this project uses

  • A deep neural network looks at the board and outputs two things: a value (how good the position is) and a policy (which moves look promising).
  • Monte Carlo Tree Search (MCTS) uses the policy to choose which moves to explore and the value to score them. Each position explored is a node.
  • Trained only by playing against itself, with no human games. DeepMind's AlphaZero (2017) introduced the method; Leela Chess Zero (Lc0) is the open-source version. check before citing
  • Why Lc0 here: it runs on the GPU, so it could check 500,000+ answers in reasonable time. T1 truth uses one pass of the network (no search). T2 truth uses 800 nodes of search.
  • Does 800 nodes matter? No, as the T2-5 check showed: at 8,000 nodes the model ranking held (ρ 0.97) and the blunder rate went from 42.0% to 42.1%.

Measuring move quality

  • Centipawn loss (CPL): how much the evaluation drops after the model's move compared with the engine's best move. 0 means the best move.
  • Clamping to ±1,000 cp: mate scores and huge evaluations would otherwise swamp the average (raw mean CPL was 4,735). Lichess clamps the same way.
  • Blunder: clamped CPL ≥ 1,000, meaning the move throws away a winning position or worse.
  • Why the engine counts as ground truth: it plays far above any human and any LLM, so its judgement is a sound reference. It is not perfect, which T2-5 tested.

Background: how LLMs work

  • Tokens: text is split into chunks (tokens). A FEN like 4k3/8/… becomes a string of tokens with no built-in notion of a board. The model only ever sees text.
  • Next-token prediction: the model is trained to predict the next token on huge amounts of web text. Everything it "knows" comes from patterns in that text, and chess text (games, FENs, puzzles) is part of it.
  • Transformers and attention: each token can look at every earlier token and weigh how relevant it is. The context window limits how much text it can see at once; Llama-3.3-70B's 512-token setting cut off 8.7% of move_only prompts (M-1).
  • Pre-training, then instruction tuning: a base model is tuned to follow instructions and chat. Reasoning ("thinking") models such as DeepSeek-R1 are trained to write out steps before answering.
  • Parameters and size: the models here range from 2B to 70B parameters. A common belief is that bigger means better; Finding 5 tests that.
  • Quantisation: storing weights in fewer bits (e.g. 4-bit) so big models fit on one GPU. This is how Ollama runs them locally.
  • Temperature and sampling: the model picks each token from a probability distribution. At the default temperature the same prompt can give different answers; here the same model gave the same move only 68.7% of the time on a repeated prompt.

Background: LLMs and chess (previous work)

Check before citing. These are well-known results recalled from memory. Find the original papers or posts and confirm the details and dates.

  • LLMs playing chess: GPT-3.5-turbo-instruct was reported to play at roughly club level (~1,750–1,800 Elo) from PGN move lists, while chat models did much worse. Suggests the prompt format and training data matter a lot.
  • Do models build an internal board? "Othello-GPT" (Li et al., 2023) found a board representation inside a model trained only on Othello moves. Karvonen (2024) found similar linear "probes" for the board in a small model trained on chess games. Those models were trained only on games; yours are general chat models.
  • Memorisation vs reasoning: a big debate in LLM research. Benchmarks can be contaminated, meaning the test items were in the training data. Lichess puzzles are public, so yours may be.
  • Chess benchmarks for LLMs: earlier ones mostly test move legality or play strength. What's new here: three tasks (evaluate, move, explain), 22 open models, 4,000 positions, engine-checked answers, chance baselines, and a fine-tuning test.

Background: fine-tuning

  • Fine-tuning: continue training a model on a small, focused dataset so it learns a specific skill.
  • LoRA (low-rank adaptation): freezes the original weights and trains small add-on matrices. Far less memory, so 3–7B models fit on one home GPU. check before citing Hu et al., 2021.
  • Held-out data: test positions must never appear in training, or the test measures memory. 20,000 training positions, none from the 4,000 benchmark positions, and 200 held-out positions for checking (F-1, F-2).
  • Your idea: if the models fail because they can't picture the board, teaching them to read it should help. Version 1 taught the piece list; version 2 taught the piece list plus every legal move.

Background: measuring fairly

  • Baselines: a score only means something next to what a dumb strategy gets. Random legal move (best move 8.8%), always answering "0" for evaluations, always naming the usually-better side (54.2%).
  • Spearman rank correlation (ρ): do the model's evaluations go up and down with the engine's? 1 = same order, 0 = no relation. Uses ranks, so huge outliers don't dominate.
  • Cohen's κ: agreement corrected for chance. 0 = no better than guessing using the class balance. Turned 46–79% direction "accuracy" into κ 0.02–0.07.
  • Bootstrap confidence intervals: resample the data many times (seeded) to see how much a number could move. Overlapping intervals mean neighbouring models are tied.
  • Pre-registration: write the pass marks down before seeing results, so you can't move the goalposts. Done for the legal-moves fine-tune (commit 1cf6cd5) and T2-5. The pieces-only criteria came after its results, and the write-up says so.

Method

PartWhat was done
Positions4,000 Lichess puzzles, 1,000 per rating tier (easy, medium, hard, extreme), seed 42
Models22 open-source models, 2B–70B, run locally through Ollama
Prompts6 formats: 3 combined (fen_only, pgn+fen, cot) and 3 single-task (eval_only, move_only, explanation_only). pgn+fen turned out identical to fen_only (Issue 23)
Records526,662
T1 · evaluateGive the evaluation in centipawns. Scored with ρ against Lc0 (one network pass) and against always answering 0
T2 · moveGive the best move. Scored for legality, then CPL against Lc0 at 800 nodes, clamped to ±1,000
T3 · explainExplain the position. Rule-based mark: names the better side (P1) and a puzzle theme (P2), whole-word matching
Move rescueIf the first move was illegal, look for a legal move elsewhere in the reply, then re-ask with the full legal-move list
Fine-tuning5 models (llama3.2:3b, gemma3:4b, qwen2.5:7b, mistral:7b, deepseek-r1:7b), LoRA, 20,000 positions, two versions, re-benchmarked against a base re-run on the same code

Results

Main conclusion (draft): the models behave like pattern matchers, not players. Five separate lines of evidence point the same way. Each is "more consistent with" pattern matching; none proves it.

1. Move quality is "perfect or disaster", and barely above chance

  • Legal moves split: 18.7% essentially perfect (CPL < 25), 4.9% strong, 12.7% decent, 21.9% very weak, 41.9% blunders. Very little in between.
  • Best move 10.2% vs 8.8% for random (1.16×). Most models 0.94–1.23×; only Gemma 4 31B/26B reach about 1.5–1.6×.
  • They play the human setup move (usually the mistake) more often than the engine's best move. Copying a familiar move is what pattern matching predicts.
  • Best: Gemma 4 31B (35.8% blunders), 26B (37.3%). Worst: Gemma 4 E2B (44.5%). Neighbouring models are statistically tied.

2. They rarely produce a legal move unaided

  • First answers legal 6.8–12.6% (five re-run models). The 97% is mostly copying from the list on the re-ask.
  • Illegal answers are stock opening moves: llama3.2:3b says "e4" 45% of the time, qwen2.5:7b "Nf6" 24%, gemma3:4b "d5" 20%, often for the wrong side.

3. Evaluations don't follow the position

  • ρ 0.11 pooled, at most 0.25. No model beats answering 0 every time (ratio 1.31–7.03).
  • Direction accuracy rises with the threshold (44.5% → 61.6% → 78.9%) but κ stays 0.02–0.07: the high numbers come from the class balance.
  • No model is reporting from the side-to-move's point of view (sign check by side).

4. Explanations name the better side less often than a fixed guess

  • 30.3% correct vs 54.2% for always naming the usually-better side. Models rarely say "Equal".
  • T3 score (0–2): Gemma 4 26B 0.76, 31B 0.66 lead; CodeLlama-34B 0.31 worst.

5. Size doesn't predict performance, except in Gemma

  • Llama 3 (3B → 8B → 70B): blunders 41.1% → 44.4% → 43.2%. No gain from 23× the parameters.
  • Qwen 2.5 (7B → 32B): 42.1% → 44.2%, slightly worse. DeepSeek-R1 7B → 14B: no gain.
  • Gemma 4 (2B → 31B): blunders 44.5% → 35.8%, ρ 0.11 → 0.24. Gemma 3 4B → 12B improves too.
  • One developer's models scaling points to training data and method rather than size. H4 not supported as a general rule.

6. Chain of thought doesn't help; answers aren't repeatable

  • cot 41.5% blunders, the same as fen_only (41.5%).
  • Same prompt twice: same move 68.7%, same side 75.0%, identical eval 34.2%.

7. Fine-tuning (section F)

  • Pieces only: board reading 1–19% → 89–99%. But ρ stayed near 0, blunder rate rose slightly for all five, and final legality fell for all five (gemma3:4b 98.7% → 58.0%). Failures were well-formed but illegal moves, even with the legal-move list in the prompt.
  • Pieces + legal moves: pre-registered criterion 0 failed. The models listed 65–81% of legal moves, with 52–60% precision. By the rule fixed in advance, no conclusion about transfer can be drawn.
  • Criterion 1 (first-answer legality +10 pts): no; best +9.3 (qwen2.5:7b). Criterion 2 (final legality held): no; fell 6–69 pts. Criterion 3 (blunders fall): only llama3.2:3b (41.0% → 38.9%); gemma3:4b's drop is a selection effect. Criterion 4 (ρ ≥ 0.10): no.
  • Takeaway: knowing where the pieces are, and approximately knowing the rules, did not make answers better or more legal.

"Is it just a notation test?"

The objection a judge is most likely to raise: FEN and SAN are hard to read, so maybe the models fail at notation, not chess. Raise it yourself and answer it with evidence.

  1. Fixing the reading didn't help. Pieces-only fine-tuning took board reading from 1–19% to 89–99%, yet evaluations, move quality and legality didn't improve; legality got worse. If notation were the bottleneck, this should have helped. Strongest point.
  2. No writing needed, still near chance. On the re-ask the models choose from a list of legal moves, so they don't produce SAN at all. They still pick the best move 10.2% vs 8.8% for random.
  3. No notation in the answer, still below a fixed guess. "Which side is better" is answered with a word. 30.3% vs 54.2%.
  4. FEN is fair input for an LLM. It is common on the web (Lichess, chess.com, forums), so almost certainly in training data, and it is the standard input in chess-LLM research. Hard for people ≠ hard for a text model.
  5. Still open: the base models were never given the position in plain English. The planned plain-board experiment (next steps, item 1) would close this.

Limitations

  • Scope: open-source 2B–70B models, local, chess only. No claims about commercial models or reasoning in general. Puzzles are tactical by design.
  • Contamination: puzzles may be in training data, which makes the failures more striking.
  • Setup position (Issue 21): the theme mark and difficulty tiers describe the next position, so they're reported but not used as evidence.
  • Move history not tested (Issue 23).
  • Reproducibility: data, engine truth and scoring are reproducible; model outputs aren't (default temperature).
  • First-answer legality only for the five re-run models.
  • Llama-3.3-70B context (M-1): 8.7% of move_only prompts cut off.
  • DeepSeek-R1 thinking mode (M-2): probably on in April, off in October; results match within 0.3 points.
  • Engine strength: checked; the ranking holds at 10× the search (ρ 0.97).
  • T3 is rule-marked, so it checks words, not reasoning.
  • Fine-tuning: only five 3–7B models; the legal-moves training fell short of its own bar.
  • Missing data: deepseek-r1:7b is missing about 4% of base evaluations.
